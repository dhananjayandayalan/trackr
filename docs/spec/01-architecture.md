## 2. The three runnable apps

| App            | Port                 | Responsibility                                                        | Talks to                                                                                                          |
| -------------- | -------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `apps/api`     | 8080                 | All REST endpoints, auth, business rules, SSE streams, search queries | Postgres (r/w), Redis, Kafka (produce via outbox + consume for SSE), Elasticsearch (read), SeaweedFS (presign)    |
| `apps/workers` | 8082 (actuator only) | Kafka consumers that build read models and send notifications/email   | Kafka (consume/produce), Elasticsearch (write), Postgres (write report + notification tables), Mailpit/SMTP       |
| `apps/collab`  | 8081                 | WebSocket relay for collaborative description editing                 | Redis (session check, presence), Postgres (`collab_update`, `collab_snapshot`), Kafka (fan-out between instances) |

Why three apps and not one or fifteen:

- **api** stays a modular monolith: in-process calls between modules are free, transactions are local, one deploy.
- **workers** are split out because their load is bursty and different (reindexing 100k issues must never slow down a board drag).
- **collab** is split out because WebSocket connections live for minutes/hours and scale by connection count, not request rate.
- All three share code through `libs/` so the boundary is a deploy boundary, not a copy-paste boundary.

## 5. Key flows

### 5.1 Move a card on the board (the hot path)

1. Browser: user drops card. UI computes a new `rank` between neighbours (fractional index), patches the board query cache immediately (optimistic), and sends `POST /api/v1/issues/MAR-131/move` with `{toStatusId, beforeKey, afterKey, expectedVersion}`.
2. api `issue` module (one transaction): load issue (`SELECT … FOR NO KEY UPDATE`), check version, check transition allowed (`workflow` API), compute rank server-side from neighbours' current ranks, update one row, insert `issue_event`, publish `IssueMoved` (+ `IssueTransitioned` if the status changed) → Modulith writes them to `event_publication` in the same transaction.
3. Commit. Response `200 {issue, warnings}` (~10–30 ms).
4. Modulith externalizer publishes the events to `trakr.issues.v1` (key = issue id) and marks the publications complete.
5. Every api instance has a realtime consumer (unique group per instance) → pushes an SSE `issue.moved` event to all browsers subscribed to project `MAR`.
6. Other browsers patch their cache (ignore if `sequence` ≤ the version they already have). The originating browser sees its own event and ignores it for the same reason.
7. Workers: `search-indexer` re-indexes the issue; `report-projector` updates today's sprint snapshot; `notifier` notifies watchers on status change.

### 5.2 Search

`POST /api/v1/search {tql}` → api parses TQL (ANTLR) → builds an Elasticsearch query → ES returns ids + highlights + sort values → api enriches nothing (the index holds every display field) → response. Freshness: ~1 s behind Postgres. The UI merges in the user's own just-made changes from cache.

### 5.3 Collaborative description

Browser opens `wss://…/collab/issues/MAR-131` → collab authenticates with the shared Redis session → checks project membership (read-only DB view) → sends stored updates → relays new updates to peers on the same instance and via `trakr.collab.v1` to other instances → appends updates to `collab_update` → clients send periodic snapshots (state + plain text + HTML) which collab stores and forwards to api through `trakr.collab.v1` (`DescriptionSnapshotted`) so the issue's searchable description updates. Full detail: 06-collab.md.

## 6. Consistency model (say this out loud until it is obvious)

| Data                                 | Consistency                                               | Why acceptable                            |
| ------------------------------------ | --------------------------------------------------------- | ----------------------------------------- |
| Postgres (issues, sprints, workflow) | Strong, transactional                                     | Source of truth                           |
| Board/backlog screens                | Strong: read from Postgres                                | Users drag here; must be exact            |
| Live updates to other users          | Eventual, ~1 s                                            | Humans don't notice 1 s                   |
| Elasticsearch search results         | Eventual, ~1 s                                            | UI overlays own changes                   |
| Reports                              | Eventual, seconds                                         | Reports are trends                        |
| Notifications/email                  | Eventual, seconds–minutes                                 | Async by nature                           |
| Description text                     | Converges via CRDT; snapshot to Postgres every ≤ 5 s idle | Merges concurrent edits without conflicts |

Delivery guarantees: outbox → Kafka is **at-least-once**. Every consumer is **idempotent** (dedupe by `event.id` in `processed_event`, or by `sequence` per aggregate).

## 7. Performance design (how we hit 00-product §8)

- Virtual threads for request handling (`spring.threads.virtual.enabled=true`) → simple blocking code, high concurrency.
- One SQL query per screen projection (jOOQ with `multiset` for nested lists) — no N+1.
- Covering index for the board: `(project_id, sprint_id, status_id, rank) INCLUDE (...)`.
- Rank moves update one row.
- HTTP: gzip/brotli via the proxy, `ETag` on GETs, `Cache-Control: no-cache` + revalidation for API, immutable hashed assets.
- Redis cache only for hot, rarely-changing reads (project + workflow metadata, 60 s TTL, evicted by events).
- Frontend: route-level code splitting, prefetch on hover/intent, optimistic mutations, list virtualisation, React Compiler.

## 9. Decision log

| #   | Decision                                              | Alternatives considered                   | Why                                                                                                 |
| --- | ----------------------------------------------------- | ----------------------------------------- | --------------------------------------------------------------------------------------------------- |
| D1  | Modular monolith api + 2 satellite apps               | Microservices per module                  | Latency, local transactions, one developer                                                          |
| D2  | JPA for writes, jOOQ for reads                        | JPA only; jOOQ only                       | Aggregates + dirty checking for commands; exact SQL for projections                                 |
| D3  | Outbox via Spring Modulith event publication registry | Debezium CDC; direct `KafkaTemplate.send` | No extra infra; never loses or invents events                                                       |
| D4  | SSE for live updates                                  | WebSocket for everything                  | One-way stream, auto-reconnect, HTTP/2 friendly; WS only where we need two-way (collab)             |
| D5  | Elasticsearch as search read model                    | Postgres FTS only; OpenSearch             | Learning goal, fuzzy + facets + highlights at scale; OpenSearch is a drop-in alternative            |
| D6  | Yjs + Java relay that never decodes CRDT state        | Node Hocuspocus sidecar; server-side CRDT | Stays Java-only; Yjs updates are commutative and idempotent so the server can store and replay them |
| D7  | Fractional indexing for rank                          | Integer positions; LexoRank buckets       | One-row writes, no rebalancing in normal use                                                        |
| D8  | Session cookie (Redis) instead of JWT in the browser  | JWT in localStorage                       | XSS cannot steal it; easy logout; shared by api and collab                                          |
| D9  | Plain CSS with layers + CSS Modules                   | Tailwind; CSS-in-JS                       | Requirement; zero runtime; learn the platform                                                       |
| D10 | SeaweedFS for local S3                                | MinIO                                     | MinIO community edition was archived in 2026                                                        |
